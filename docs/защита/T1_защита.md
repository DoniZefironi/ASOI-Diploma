## 0. Что это вообще такое, на пальцах

Представь сайт-помощник для абитуриента/студента, который отвечает на вопрос **«какая IT-специальность мне подходит и как до неё дойти»**.

Пользователь:
1. Проходит несколько психологических тестов (вопросы типа «нравится ли тебе разбирать технику» — да/нет).
2. Система считает баллы и говорит: «тебе подходит специальность Х, потому что у тебя высокие баллы по логике и технике».
3. Дополнительно AI (как ChatGPT, но от Google — Gemini) пишет пошаговый план обучения: «месяц 1 — выучи основы Python, месяц 2 — алгоритмы, ...».
4. Дальше пользователь может пойти на факультатив по этой специальности, поучаствовать в олимпиаде по программированию (с автоматической проверкой кода) или посмотреть вакансии стажировок.

Всё это — один сайт (Next.js фронтенд) + один сервер с базой данных (NestJS + PostgreSQL).

## 1. Технологии — что это и почему именно так (на пальцах)

### 1.1 NestJS — «бэкенд» (серверная часть)

**Аналогия**: представь ресторан. Без NestJS — это кухня без разделения труда: один повар бегает и готовит всё подряд, в любом порядке, легко что-то забыть или сломать. NestJS — это ресторан с **цехами** (модулями): отдельный цех для профориентации, отдельный для олимпиад, отдельный для факультативов. В каждом цехе:
- **Controller** — официант, который принимает заказ («дай мне результаты теста для пользователя 5») и передаёт его дальше;
- **Service** — повар, который реально готовит блюдо (считает баллы, ищет в базе);
- **Entity** — карточка рецепта, описывающая, какие «ингредиенты» (поля/столбцы) есть у блюда (записи в таблице БД).

**Почему так, а не иначе**: проект — это **три дипломные работы в одном коде** (T1/T2/T3), и без разделения на цеха-модули код превратился бы в один огромный файл, в котором три разных человека постоянно мешают друг другу. NestJS даёт «коробки» (модули), внутри которых каждый работает со своим цехом, не трогая чужой.

**Почему именно NestJS, а не Django (Python) или Spring (Java)**: фронтенд и так пишется на TypeScript (React/Next.js). NestJS — тоже TypeScript. Значит, типы данных (например, «результат теста — это объект с полями testType и answers») можно использовать **и на фронте, и на бэке без перевода** — меньше шансов на ошибку «здесь поле называется иначе».

### 1.2 PostgreSQL + TypeORM — «база данных»

**Аналогия**: PostgreSQL — это огромный шкаф с папками (таблицами). Каждая папка — это, например, «Результаты тестов профориентации», и в ней лежат листочки (строки), у каждого листочка одинаковая форма с полями: «ID пользователя», «Результат теста», «Рекомендованная профессия» и т.д.

Но иногда форма листочка слишком жёсткая — например, у теста Холланда 30 вопросов, у теста Климова 20, и у каждого своя структура. Заводить под каждый тест отдельную таблицу — overkill. Поэтому в PostgreSQL есть «карман для всего подряд» — поле типа **jsonb**, куда можно положить произвольный JSON-объект (как файл .json внутри листочка). Так и хранятся вопросы тестов (`career_tests.questions`) и результаты (`professional_orientations.testResult`).

**TypeORM** — это переводчик между «объектами в коде» (JS/TS) и «листочками в шкафу» (строками таблицы). Ты пишешь класс с аннотациями:

```typescript
@Entity('career_tests')
export class CareerTest {
  @PrimaryGeneratedColumn() id: number;
  @Column({ unique: true }) type: string;       // 'holland' | 'klimov'
  @Column({ type: 'jsonb' }) questions: any[];  // вопросы — как json-файл внутри строки
}
```

— и TypeORM сам пишет SQL-запросы для создания таблицы, чтения/записи строк и т.д. Без TypeORM пришлось бы вручную писать `INSERT INTO career_tests (...) VALUES (...)` для каждой операции.

**Почему PostgreSQL, а не MongoDB (чисто документная база)**: в системе очень много **связей** — пользователь связан с группой, группа с курсом, тест — с пользователем, заявка на стажировку — с пользователем и со стажировкой. Это классические «таблица А ссылается на таблицу Б» (foreign key) — то, для чего реляционные базы (PostgreSQL) созданы изначально. При этом для «нестандартных» кусков данных (вопросы тестов) PostgreSQL даёт jsonb — то есть берёт лучшее из обоих миров.

### 1.3 Next.js + React — «фронтенд» (то, что видит пользователь)

**Аналогия**: React — это LEGO для сайтов: ты строишь страницу из маленьких многоразовых деталей (кнопка, карточка, форма). Next.js добавляет к этому **автоматические адреса**: если ты создал папку `app/career-test/page.tsx`, страница сама становится доступна по адресу `сайт.ру/career-test` — никакого отдельного файла-«роутера» с ручными правками не нужно.

### 1.4 Docker-песочница для компилятора (используется олимпиадами)

**Аналогия**: представь, что студент присылает свой код на проверку. Запускать его код **прямо на главном сервере** — то же самое, что пустить незнакомца с улицы готовить у себя на кухне: а если он специально (или по ошибке — `while(true){}`) устроит беспредел — зависнет навечно, сожрёт всю память, попытается полезть в интернет?

Решение — **отдельная одноразовая «комната для тестов» (Docker-контейнер)**:
- у комнаты нет доступа в интернет (`NetworkMode: none`);
- ограничен «запас еды» — 100 МБ памяти;
- ограничено «время приёма» — 0.5 процессора и **10 секунд**, после чего комнату принудительно закрывают;
- ограничено число «людей в комнате» — 100 процессов (защита от программ, которые бесконечно запускают сами себя — fork bomb);
- после теста комната **полностью уничтожается** (`container.remove({force: true})`), независимо от того, что там происходило.

Код передаётся в комнату не файлом, а закодированным в текст (base64) прямо в команде запуска — чтобы не давать программе лишних точек контакта с внешней файловой системой.

**Почему Docker, а не «песочница внутри Node.js» (vm2 и т.п.)**: нужно поддержать **4 разных языка** (JS, Python, C++, Java) с одинаковыми гарантиями. У каждого языка — свой Docker-образ (`sandbox-node`, `sandbox-python`, `sandbox-cpp`, `sandbox-java`), но правила изоляции (память/CPU/сеть/время) одинаковые для всех, потому что это настройки самого контейнера, а не особенности языка.

### 1.5 Google Gemini 2.0 Flash — генератор плана обучения

**Аналогия**: это как если бы ты написал в ChatGPT: «Я хочу стать Backend-разработчиком, у меня хорошо с логикой и вниманием к деталям — составь мне план обучения на несколько месяцев». Gemini генерирует **связный текст с конкретными шагами** (а не просит пользователя гадать самому).

Технически: бэкенд формирует текстовый запрос (промпт) с описанием специальности, баллами по чертам личности и списком «сработавших правил» (см. ниже), отправляет его на:

```
POST https://generativelanguage.googleapis.com/v1beta/models/gemini-2.0-flash:generateContent
generationConfig: { maxOutputTokens: 2048, temperature: 0.7 }
```

`temperature: 0.7` — это «креативность» ответа: 0 = всегда одинаковый сухой ответ, 1 = более «живой», но менее предсказуемый текст. 0.7 — баланс: текст звучит по-человечески, но не уходит в фантазии.

**А что если Google недоступен/лимит исчерпан?** Тогда срабатывает **запасной вариант** — заранее написанный шаблонный план для каждой специальности (`generateRoadmapLocally()`). Пользователь в любом случае получает план, просто менее персонализированный — система никогда не показывает пользователю «ошибка, попробуйте позже».

## 3. Экспертная система профориентации — самое главное, разбираем по шагам

Это — ядро T1. Разберём максимально подробно: что вводит пользователь, что считается внутри, что получается на выходе.

### 3.1 Уровень 1 — тесты Холланда и Климова (backend)

**Тест Холланда** — это 30 вопросов вида «нравится ли тебе...?», ответ — да (1) или нет (0). Каждый вопрос помечен одной из 6 букв: **R, I, A, S, E, C** (Реалистичный, Исследовательский, Артистичный, Социальный, Предприимчивый, Конвенциональный — это стандартные категории методики Холланда).

Пример вопроса:
```
{ id: 1, text: 'Собирать и настраивать компьютерное оборудование', category: 'R' }
{ id: 6, text: 'Исследовать данные и выявлять закономерности', category: 'I' }
```

**Как считаются баллы — пошагово**:

1. У пользователя есть массив ответов: `[1, 0, 1, 1, 0, 1, ...]` (30 чисел, по одному на каждый вопрос).
2. Система идёт по всем вопросам один за одним. Если ответ на вопрос = 1 (да), то к счётчику категории этого вопроса добавляется +1:
   ```typescript
   test.questions.forEach((q, idx) => {
     if (answers[idx] === 1) scores[q.category] = (scores[q.category] ?? 0) + 1;
   });
   ```
   Грубо: «сколько раз пользователь ответил "да" на вопросы про букву R», «сколько раз — про I» и т.д.
3. В итоге получается, например:
   ```
   scores = { R: 12, I: 8, A: 5, S: 4, E: 3, C: 6 }
   ```
   (12 «да»-ответов на вопросы про R, 8 — про I, и т.д.)
4. Находим категорию с **максимальным** числом — это `topType`. В примере `topType = 'R'` (12 — самое большое число).
5. У каждой категории заранее (в `categoryMeta`, тоже в БД) записан список подходящих профессий. Для `R` это, например, `['IoT-инженер', 'DevOps-инженер', 'Инженер-электронщик']`.
6. Пользователю показывается: «Ваш тип — Реалистичный (R). Вам подходят: IoT-инженер, DevOps-инженер, ...».

**Тест Климова** работает похоже, но вопросы — не «да/нет», а **выбор из двух вариантов** (a или b), и категории — другие, например `ЧЧ` («человек-человек», профессии про общение с людьми) и `ЧТ` («человек-техника»):
```
{
  id: 1,
  a: { text: 'Проводить обучение и тренинги для сотрудников', category: 'ЧЧ' },
  b: { text: 'Настраивать сетевую инфраструктуру и серверы', category: 'ЧТ' }
}
```
Считается аналогично: за каждый выбор «a» или «b» прибавляется +1 категории выбранного варианта, в конце берётся категория-победитель.

**Совмещение двух тестов**. Если пользователь прошёл ОБА теста, система смотрит на пару «топ-категория Холланда» + «топ-категория Климова» — например, `R + ЧТ` — и ищет в заранее составленной таблице соответствий (`RULES_MATRIX['R+ЧТ']`) готовый список профессий с **уверенностью в процентах** (`confidence`), например: IoT-инженер — 95%, Embedded-разработчик — 92%. Каждой профессии соответствует подробная карточка (`CAREER_PROFILES`): описание, нужные навыки, инструменты, зарплатная вилка.

**Зачем такая простая арифметика (а не «умный ИИ»)?** Тесты Холланда и Климова — это **проверенные психологические методики**, у которых правила подсчёта уже придуманы психологами десятилетия назад и описаны в методичках. Задача программы — просто честно посчитать по этим правилам, а не «угадывать» что-то самостоятельно.

### 3.2 Уровень 2 — расширенная экспертная система (frontend), 40 вопросов

Это более продвинутая часть, работает **прямо в браузере пользователя**, без сервера (мгновенно).

**Вход**: 40 вопросов, разбитых на 4 блока по 10:
1. «Как ты мыслишь» (логика, аналитика)
2. «Твои реакции» (эмоции, стресс)
3. «Как ты работаешь» (организованность, командная работа)
4. «Честно о себе» (самооценка)

На каждый вопрос ответ — **не да/нет**, а по шкале от 0 до 4 (5 вариантов): «Нет» (0), «Скорее нет» (1), «Не уверен» (2), «Скорее да» (3), «Да» (4).

**Шаг 1 — считаем «черты личности» (traits)**

У каждого вопроса есть «вес» по нескольким чертам. Например, вопрос «Мне нравится разбираться, как что-то устроено внутри» может иметь вес `{logical: 2, technical: 3}` — то есть это вопрос больше про «техническую склонность» (вес 3), но немного и про логику (вес 2).

Ответ переводится в множитель через таблицу:
```typescript
const LIKERT_MUL = [0, 0.25, 0.5, 0.75, 1.0];
// ответ 0 ("Нет")        → множитель 0    (вопрос не добавляет ничего)
// ответ 2 ("Не уверен")  → множитель 0.5  (добавляет половину веса)
// ответ 4 ("Да")         → множитель 1.0  (добавляет полный вес)
```

Для каждой черты суммируются `вес × множитель` по всем вопросам, где эта черта упоминается, а затем сумма **нормируется** в шкалу 0–10 (делится на максимально возможную сумму и умножается на 10). В итоге получается, например:
```
traits = { logical: 8.5, technical: 9.2, detail: 6.1, creative: 3.4, ... }
```
То есть — «насколько сильно у пользователя выражена логика, техническая склонность и т.д., от 0 до 10».

**Шаг 2 — продукционные правила («если... то...»)**

Дальше идёт **база правил**, каждое выглядит так:

```typescript
{
  id: 'BE-1',
  career: 'backend-dev',
  cf: 0.82, // "уверенность" этого правила, если оно выполнится
  description: 'Сильное логическое мышление + техническая склонность + внимание к деталям',
  conditions: [
    { trait: 'logical',   op: '>=', value: 7 },
    { trait: 'technical', op: '>=', value: 6 },
    { trait: 'detail',    op: '>=', value: 5 }
  ]
}
```

Читается так: **«ЕСЛИ** logical ≥ 7 **И** technical ≥ 6 **И** detail ≥ 5, **ТО** это похоже на Backend-разработчика, и я уверен в этом на 82%»**.**

Программа проходит по **всем** правилам в базе (десятки штук) и для каждого проверяет — выполнились ли ВСЕ его условия. Если да — правило «сработало» (`fired`), и его `cf` и `description` запоминаются.

В нашем примере: `logical=8.5 ≥ 7` ✅, `technical=9.2 ≥ 6` ✅, `detail=6.1 ≥ 5` ✅ — все условия правды → правило **сработало**.

**Шаг 3 — как объединить несколько «сработавших» правил в одну итоговую уверенность (формула MYCIN)**

Допустим, для специальности «Backend-разработчик» сработали ДВА правила: одно с уверенностью 0.8, второе — с уверенностью 0.6. Какая итоговая уверенность?

**Неправильно** просто сложить: 0.8 + 0.6 = 1.4 = 140% — уверенность больше 100% не имеет смысла.

**Правильная формула** (используется в исторической медицинской экспертной системе MYCIN):

```
CF_новое = CF_старое + CF_правила × (1 − CF_старое)
```

Считаем по шагам:
- Берём первое правило: `CF = 0.8`.
- Добавляем второе правило: `CF_новое = 0.8 + 0.6 × (1 − 0.8) = 0.8 + 0.6 × 0.2 = 0.8 + 0.12 = 0.92`.

**Итог: 92%.**

**Почему так — простыми словами**: представь уверенность как **заполнение стакана** до краёв (100%). Первое правило наливает 80% стакана. Второе правило по идее «должно» налить ещё 60%, но **в стакане осталось место только на 20%** (1 − 0.8). Поэтому оно наливает 60% **от оставшегося места** (0.6 × 0.2 = 0.12), и стакан становится заполнен на 92%. Чем больше независимых правил подтверждают одну и ту же специальность — тем ближе уверенность к 100%, но **она никогда не "перельётся"** за край.

**Шаг 4 — итог**

Для каждой специальности, у которой сработало хотя бы одно правило, считается итоговый CF (по формуле выше, если правил несколько). Специальности сортируются по итоговому CF — пользователю показываются топ-варианты с процентами уверенности и списком «почему» (описания сработавших правил).

### 3.3 Полный пример «от начала до конца»

1. Пользователь отвечает на 30 вопросов теста Холланда → `topType = 'R'`, рекомендуемые профессии: IoT-инженер, DevOps-инженер...
2. Пользователь отвечает на 20 вопросов теста Климова → `topType = 'ЧТ'`.
3. Система смотрит `RULES_MATRIX['R+ЧТ']` → топ-1: **IoT-инженер**, уверенность 95%.
4. Параллельно (или вместо этого) пользователь проходит расширенный тест на 40 вопросов → получает `traits = {logical: 8.5, technical: 9.2, detail: 6.1, ...}`.
5. По traits срабатывают правила, например `BE-1` (Backend, CF 0.82) и ещё одно правило для Backend с CF 0.6 → комбинированная уверенность 92% (см. формулу выше).
6. Пользователь выбирает специальность (например, IoT-инженер) → нажимает «составить план обучения» → запрос летит в Gemini вместе с данными о его чертах и описаниями сработавших правил → Gemini пишет персональный план на 4–5 этапов.

### 3.4 Зачем два разных «движка» (backend rules + frontend MYCIN)?

- **Тесты Холланда/Климова** — стандартные, «сертифицированные» методики с фиксированными правилами подсчёта. Их логично хранить и считать на сервере (один раз заданы — и не меняются).
- **Расширенная система на 40 вопросов** — собственная разработка, которая должна быть **отзывчивой** (мгновенный результат при ответе на каждый вопрос, визуализация черт по ходу теста) — поэтому считается прямо в браузере, без задержки на сетевой запрос.
- Обе системы **не противоречат**, а дополняют друг друга: финальный AI-роадмап использует данные именно из расширенной (frontend) системы — она даёт более детализированный «портрет» пользователя (9+ черт против 6 категорий Холланда).

## 4. Факультативы (Electives) — простыми словами

Это как запись на кружок/секцию:
- Администратор/ментор создаёт факультатив (`Elective`): название, описание, привязка к группе, преподаватель, даты, лимит мест.
- Студент видит список доступных факультативов (`GET /electives`) и записывается (`POST /electives/:id/enroll`) — создаётся запись в `elective_enrollments` со статусом `active`. Если расхотел — `DELETE /electives/:id/enroll`, статус становится `cancelled`.
- У факультатива могут быть свои задания и расписание занятий — это управляется через `/electives/:id/assignments` и `/electives/:id/schedule` (только ментор/админ).
- Уникальность `(electiveId, userId)` в таблице записей гарантирует, что нельзя записаться на один и тот же факультатив два раза.

## 5. Олимпиады по программированию — простыми словами

Это мини-версия Codeforces/LeetCode внутри платформы:
- `Olympiad` — соревнование с датами начала/конца, дедлайном регистрации и списком разрешённых языков (по умолчанию JS/Python/C++/Java).
- `OlympiadProblem` — задача: текст условия, описание входных/выходных данных, примеры (`examples`), сложность (`easy/medium/hard`), сколько баллов даёт.
- `OlympiadSubmission` — посылка решения: код, язык, и **статус, который выставляется автоматически**:
  - `pending` — ещё проверяется,
  - `accepted` — все тесты прошли,
  - `wrong_answer` — вывод не совпал с ожидаемым,
  - `error` — код не скомпилировался/упал с ошибкой.

**Как происходит проверка**: посылка отправляется в тот же Docker-«песочницу», что описана в разделе 1.4 — код реально выполняется в изолированном контейнере, его вывод сравнивается с ожидаемым ответом задачи. Никакой человек не проверяет решения руками — это полностью автоматический процесс, как на настоящих сайтах-«судьях» (online judge).

## 6. Стажировки (Internships) — простыми словами

Это доска объявлений о стажировках, чем-то похожая на hh.ru:
- `Internship` — карточка вакансии: компания, описание, требования, формат (офис/удалёнка/гибрид), зарплата, дедлайн, теги. Поля `source`/`externalId` показывают, что вакансия может быть либо создана вручную, либо **импортирована с внешнего сайта** (например, hh.ru).
- `InternshipApplication` — «я откликнулся на эту вакансию» (с уникальностью — нельзя откликнуться повторно).
- `InternshipView` — «я посмотрел эту вакансию» + счётчик `viewCount` — простая аналитика популярности вакансий.

## 7. Итоговая «защитная» формулировка (короткая)

T1 — профориентационная система с **двухуровневой экспертной системой**:
- Уровень 1 (сервер) — классические психометрические тесты Холланда и Климова: простой подсчёт баллов по категориям, объединение результатов через готовую таблицу соответствий.
- Уровень 2 (браузер) — собственная продукционная система из 40 вопросов, 9+ черт личности и десятков правил вида «если черты ≥ порогов → специальность с уверенностью CF», где уверенность нескольких сработавших правил комбинируется по формуле MYCIN (`CF_new = CF_old + CF_rule×(1−CF_old)`) — нелинейное «дозаполнение» уверенности, никогда не превышающее 100%.

Результат уточняется генеративным AI (Gemini 2.0 Flash) в виде персонального плана обучения (с офлайн-резервом на случай недоступности AI). Вокруг — практическая инфраструктура: факультативы (запись/отписка), олимпиады с полностью автоматической проверкой кода в изолированной Docker-песочнице (память/CPU/сеть/время под жёсткими лимитами), и каталог стажировок с откликами и аналитикой просмотров.
